# 3.3.0rc3: read-only probe targets

This unpublished candidate extends the controller-family beta with active probe
target temperatures and target ranges. It also preserves modern zero-valued
plan, step and prompt IDs instead of replacing them with legacy fields.

Cloud traffic retains the empty status/capability reads (`0x05`, `0x07`, `0x0E`)
and adds only a validated `0x0B` probe-program read with a two-byte selector.
It sends no settings, target changes, ignition or cooking-program writes.

Program decoding is based on the installed OEM Android app 2.13.0.2704; see the
[source comparison](2026-11-10-oem-comparison.md). Responses match the pending read window and embedded probe/program/plan,
with pending data reset on session changes. Controller response sequences are
independent of the request; the payload does not echo a session ID. Only the current step
supplies a target, using both exit criteria and prompt triggers. Ranges use two sensors; absent or ambiguous targets stay
unknown. An ambiguous controller error keeps normal recovery behavior and suspends
optional reads until the integration is reloaded. Diagnostics expose that state. Cache age,
session transitions and reconnects prevent indefinite reuse of old targets.
Only one program read per slot may be outstanding. Its original session record
survives session replacement, including disappearance and reuse of the same IDs,
so a late reply is discarded before another read is sent. A missing reply keeps
that slot's optional targets unknown until it arrives or the connection resets;
ordinary temperature updates continue. No guessed retry delay can establish
response ownership because the protocol does not echo a request or session ID.

New [automated](3.3.0rc3-rc-automated.json) and
[physical](3.3.0rc3-rc-physical.json) records must bind the exact runtime.
Historical RC2 and earlier receipts do not qualify this candidate. The
[product matrix](../product-compatibility.md) preserves the other controller
issues and per-device gates.

The prior runtime `8b1f0b9191b6` [targeted live trial](3.3.0rc3-probe-target-observation.json) passed on the
existing Connect Hub and Samsung tablet: single target creation/edit/removal,
range creation/edit/removal, repeated refresh, HA restart with an active range,
entry reload with an active target, and retention of all 18 baseline entity IDs.
Edits appeared in approximately 2–3 seconds; initial range creation took about
21 seconds. Active-target entry reload recovered in about 21 seconds. Removals
cleared within the first two local state polls. The trial exposed and corrected queued stale status:
the socket now consumes incoming frames between its ten-second status polls.

The final follow-up limits between-poll fast recovery to one attempt per poll
window; a second failure reaches normal backoff. Its native regression exercises
a gateway that repeatedly delivers status and then drops the connection. A fresh
installed-runtime observation will accompany the published beta; the prior
trial above does not qualify changed runtime bytes.

Full stable promotion still requires the repository's physical matrix and
endurance gates, plus exact-head CI and review. No other grill is qualified by
this Hub trial. The installed candidate remains unreleased.
