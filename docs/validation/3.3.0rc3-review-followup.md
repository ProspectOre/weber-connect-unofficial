# RC3 review follow-up

Disposition of the five P3 notes in [PR 97's review](https://github.com/ProspectOre/weber-connect-unofficial/pull/97#pullrequestreview-5855342302).

- **Missing aggregate check:** the PR-edit helper waits only while an older run
  of the same workflow and head is queued or running. Missing, completed or
  approval-held runs fail with an actionable message. Tests cover both the
  creation race and the absence of a viable code run.
- **Diagnostics assertions:** tests now check single/range/absent target values
  and both states of the optional-read suspension flag.
- **Late replies:** each slot has at most one outstanding read, owned by its
  original session record. Replacement or disappearance does not release that
  owner. A reply for a retired record is discarded before a new read is sent,
  including reuse of every wire-visible ID. An expired window does not authorize
  another request; a missing reply leaves optional targets unknown until it
  arrives or the connection resets. Tests cover these transitions and malformed
  replies without relying on a guessed delay or gateway behavior.
- **Temperature bounds:** retained the OEM decoder's signed-int32 semantics.
  OEM 2.13 `CookProgramPayloadKt.readTriggerCriteria`, `TriggerCriteria`,
  `CookProgram.ProbeTempAbove/Below`, and `GetCookTargetsInfoUseCaseKt` apply no
  sentinel or range validation to incoming probe triggers. The Hub's manual-food
  editor permits 60–570°F, but that UI range does not establish a decoder-wide
  bound for recipes, ranges and other controllers. No extreme real-world target
  or sentinel was observed. The negative synthetic fixture verifies decoding,
  not a physically meaningful target; imposing an arbitrary range would change
  protocol semantics without evidence.
- **Between-poll recovery:** restored the bounded, one-shot fresh-connection
  recovery used by polling, including normal failure reporting if it fails.
  Stop/wake requests do not open a replacement socket. The one-second poll
  floor is restored. Tests cover closed sockets, I/O errors, timeouts, failed
  recovery, stopping and the poll floor.

Physical verification remains bound to the runtime fingerprint in the
[targeted observation](3.3.0rc3-probe-target-observation.json). These fixes do not
establish compatibility with untested controllers or full stable acceptance.

The [second review](https://github.com/ProspectOre/weber-connect-unofficial/pull/97#pullrequestreview-5855932123) found two further P3 issues:

- A poll window now permits only one fast recovery. A replacement that delivers
  status and immediately fails reaches the existing error/backoff path instead
  of opening another connection. A regression checks the second failure, one
  handshake, one successful recovery and closure of both sockets. Backoff now
  resets only after a healthy polling interval, so a brief status followed by
  another disconnect does not pin repeated retries at one second. A separate
  regression verifies escalating delays and reset after a healthy interval.
- The CI-helper stub now feeds realistic API JSON through the actual jq filters.
  Fixtures distinguish the current/future check suites, inactive or approval-held
  runs, queued and running predecessors, other apps, cancelled/skipped checks
  and success/failure propagation. The contributor guide lists jq as a test
  prerequisite and correctly distinguishes hosted CI from shared `/review`.

The [third review](https://github.com/ProspectOre/weber-connect-unofficial/pull/97#pullrequestreview-5856052669)
confirmed the cross-cycle backoff gap. The common cause was treating a received
status as a healthy polling interval; the reset now follows the completed
listener interval. The multi-cycle regression covers 1, 2, 5, 10, 30, 30 second
delays, then a healthy interval and reset to 1, 2 seconds. This tests both the
cap and recovery instead of stopping after the first error callback.

Its receipt-count note is addressed by a fresh complete minimum-HA run after
receipt refresh: 720 tests and five subtests pass, with 100% statement/branch
coverage. The current-HA receipt explicitly awaits the new hosted run.

The syntax finding is a false positive for this project's Python >=3.14 floor.
[PEP 758 in Python 3.14](https://docs.python.org/3.14/whatsnew/3.14.html#pep-758-allow-except-and-except-expressions-without-brackets)
permits multiple exception types without grouping parentheses when no `as`
clause is used. Both handlers compile under Python 3.14.10, and the native suite
imports and exercises them. No compatibility claim is made for Python 3.13.
