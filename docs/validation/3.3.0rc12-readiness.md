# 3.3.0rc12: SiLabs pairing waits for approval

This unpublished candidate changes how SiLabs controller setup waits for the
controller's answer. Candidate numbers 4 to 11 belonged to unpublished builds
and are not reused.

## Cause

[Issue 59](https://github.com/ProspectOre/weber-connect-unofficial/issues/59)
reports an EP-series thermometer on 3.3.0rc3: services ready, pairing request
sent, then `failed` with `timeout` 0.1 seconds later, on both an ESPHome proxy
and a local BlueZ adapter. The support report places the failure at the SiLabs
transport wrapper.

The response characteristic is `read`+`notify`. After writing the request, the
rc3 response channel read that characteristic whenever no notification was
queued, and treated a failed read as fatal. A SiLabs controller answers only by
notification after physical approval, so the immediate read failed and setup
abandoned the request and disconnected before approval was possible. The
reporter's "the thermometer drops the link" observation is consistent with that
integration-side disconnect. The working Saber path already treats such reads as
optional.

## Change

- A subscribed notification stream is the only response source; reads are a
  fallback only when the characteristic cannot notify or subscription fails.
- Pairing and stored-key reconnect watch the connection. A link drop ends the
  wait at once with `appliance_disconnected`, so a genuine controller drop is
  distinguishable from an integration abort or an approval timeout.

A synthetic controller that rejects reads and answers by delayed notification
fails on rc3 with the reported message and location, and passes here.

## Not established

The secure-session handshake, capability negotiation, cloud association and
live readings on any EP-series or Genesis controller remain unverified. One
reported ESPHome attempt stalled for about eight seconds inside the request
write itself; this change does not address that path. New
[automated](3.3.0rc12-rc-automated.json) and
[physical](3.3.0rc12-rc-physical.json) records bind this exact runtime;
earlier receipts do not qualify it. The
[product matrix](../product-compatibility.md) keeps per-device gates.
